# AI Product Image Generator

## Product scope

- This is an image-only product imagery application. Prompts are text, and all uploaded/reference/mask/generated media must be validated image files.
- PDF, video, audio, arbitrary files, and public media URLs are intentionally out of scope. Do not advertise or partially implement those model capabilities.
- Each selected product image creates an independent generation job. Shared reference images may be attached to each job subject to that model's limits.
- When the user says "add new models", check the entire current Vercel AI Gateway catalog across ALL providers and official provider documentation, then add every missing model that accepts BOTH text prompts AND uploaded images and produces images. Do not restrict discovery to OpenAI/Google or to recently released models. Image understanding with text-only output and text-to-image-only models do not qualify.
- For each "add new models" pass that adds models, show a visible "New" tag in the model selector for every model added in that pass. Replace the previous pass's "New" tags so only the latest additions carry the tag. Track this with explicit per-model metadata, separate from lifecycle labels such as recommended/current/legacy; do not infer it from model names or provider release dates. If the pass adds no models, leave the existing tags unchanged. Keep model-addition pass metadata in `schemas/image-model-discovery.ts`; use a unique pass identifier, including a suffix when multiple passes happen on the same date.
- Order the model selector with user favourites first, then models tagged "New", then the remaining models. Preserve curated order within each group. Provide an accessible heart toggle for favourites and persist those choices across reloads. Model-refresh passes must preserve user favourites; marking or unmarking a favourite must not change the selected model or its settings.
- Complete each model addition through the exact-ID profile, strict settings schema, selector/settings UI, Gateway adapter, reference/mask validation, output accounting, stored settings/replay, and regression coverage. Verify actual image-edit/reference support in official documentation; catalog modality metadata alone can omit image inputs. Keep unavailable models clearly marked, and report eligible models that Gateway cannot yet serve. This shorthand does not authorize production deployment.

## Stack and integration boundaries

- Read the ignored `private-agents.md` when present for locally scoped development resource IDs. Keep credentials in ignored environment files or platform secret variables, never in either agents file.

- Framework: Nuxt 4 on Node 26.
- Railpack must install `libatomic1` in both the build and final runtime image through `railpack.json`. Node 26 requires `libatomic.so.1` on Linux. Deployment checks must verify the final runtime's shared libraries; a successful build alone is insufficient.
- Coolify currently uses Railpack 0.23.0. Use explicit Apt package names in `railpack.json`; do not use the `"..."` list-extension syntax from newer Railpack documentation, because this version can pass it literally to `apt-get`. Check configuration compatibility against the deployed Railpack version.
- ORM/database: Drizzle with PostgreSQL. Runtime code must not fall back to a local SQLite file.
- Uploaded and generated images live in a private S3-compatible Railway bucket. Runtime file operations must use the storage backend; do not require a local disk or persistent app volume. Keep object keys within the configured prefix and serve images through authenticated endpoints.
- HTTP image operations must use `useUserFS` with the authenticated account and PostgreSQL asset registry. Raw `useFS` is reserved for authorized internal maintenance/imports. Organization owners administer membership, not other users' private assets or generation history. Sharing is view-only, limited to users in the same organization, and inherited through logical folder ancestry. Recipients may preview, download and use images in generations; legacy edit grants must also resolve to view-only access.
- Uploaded object URLs are immutable and separate from logical folder names. Delete only exact authorized registered keys; never recursively delete a physical user prefix or infer access from a path prefix. Legacy objects require explicit bootstrap-owner adoption before HTTP access.
- Generative AI calls must use Vercel AI SDK through Vercel AI Gateway. Do not add direct provider SDK/API calls. The user explicitly authorized local BiRefNet background removal: only the two pinned CPU ONNX profiles in `schemas/background-removal-models.ts` may run outside Gateway, in a bounded Node worker process inside the existing app service.
- Curated image-model profiles and their runtime schemas live in `schemas/image-generation.ts` and `schemas/catalog-image-models.ts`. Record the catalog audit and exclusions in `docs/image-model-catalog.md`. Exact model IDs and discriminated settings—not names, descriptions, or regex heuristics—must choose adapters and capabilities.
- All Gateway providers are in scope. Keep an explicit, verified per-model whitelist and record exclusions when a catalog model cannot use uploaded pictures through Gateway or returns unsupported media such as SVG.

## Model settings and resolution

- Image resolution is not uniform across models. Never expose one generic size/aspect UI to every model.
- Each model profile must declare its own settings component, defaults, allowed aspect ratios/sizes, reference limits, tools, warnings, and adapter.
- The client derives controls from the selected profile, resets incompatible settings synchronously when the model changes, and never sends stale settings from another model family.
- Shared Zod schemas are the request boundary. The server must parse and enforce the selected profile even when the UI has already validated it; never restore `as any` forwarding of provider options.
- Persist the normalized requested/effective model and settings used for every generation. Regenerate/refine must replay the exact stored image sources and settings or clearly report that exact replay is unavailable.
- Record actual returned image MIME type, byte size, width, and height. Do not infer output dimensions from requested settings.

## Generation reliability

- Provider calls require a bounded timeout/abort signal and normalized, redacted, retryable timeout errors.
- Generation concurrency and queue depth are bounded across all instances through PostgreSQL leases, with process-wide memory limits as an additional safeguard. Reject overload with an explicit `429`; never accumulate an unbounded queue of future paid calls. Interactive generation stays awaited within a bounded request lifetime. The user explicitly requested pipeline batches to continue after closing the browser: pipeline paid work runs only as an awaited, bounded job in the dedicated Git-deployed pipeline worker, never as detached work inside an HTTP handler.
- Create pending rows before provider work. Terminal state changes must be atomic and conditional on `status = 'pending'`; a failed sibling must never overwrite a successful output.
- Recover abandoned pending rows using a conservative stale timeout or durable lease/heartbeat. Process start time is not job ownership and must not be used to fail another worker's live job.
- Persist every provider output independently, release image buffers promptly, and clean up only the exact output file whose persistence failed.
- Capture bounded/redacted provider diagnostics, request IDs, attempt data, retryability, warnings, and billing for every attempt. Never expose credentials, image bytes/data URLs, cookies, absolute filesystem paths, or directory listings in API errors.
- Hold generated images until an exact completed non-BYOK Gateway charge is confirmed. Apply this to public history projections, S3 serving, asset lists, sharing, favorites and generation references. A valid zero charge unlocks; estimates never unlock. Uploaded images are unaffected.
- Local background removal uses its own bounded PostgreSQL queue and conservative leases, one running inference across instances, a killable child process, and immutable private S3 output. Preserve originals, recheck source access before reading and publishing, and register processed assets atomically with job success. Its known zero provider charge is `local-processing`, never a fabricated Gateway charge; it does not debit user credit. Idle apps must not poll the database indefinitely.
- People profiles are private by default; organization owners have no automatic access to another user's profiles. Explicit profile grants allow same-organization recipients to view, download and use live photos as references, including future confirmed photos, without editing the profile or adding generations to its owner's profile. Profile-derived photo access must recheck the live profile, owner, recipient, share and photo association; revocation, unlinking, profile removal and owner disablement withdraw that access while preserving independent file/folder grants. Keep profile names, descriptions and photo associations in PostgreSQL; reuse immutable authorized image assets in S3. Persist an owned person association before paid generation work. Person photos, covers and counts must exclude deleted, expired and unpriced generated outputs. Unlinking photos or deleting a profile must preserve image objects, charges and generation history. All People generations use the current Gateway profiles, exact-price gate, bounded admission and user credit accounting.
- Pipelines are private, strict image/text DAGs with no arbitrary code or external media URLs. Save edits with revision checks and freeze each run's graph, parameters and independent batch inputs. Use durable PostgreSQL claims and a committed provider-start fence before every paid call; associate pending generation rows with the step before work starts. Each paid wave gets fresh credit admission and a server-created batch ID. All generated intermediate images and utility text remain held until exact prices settle; never pass raw unpriced buffers to later nodes. An uncertain interrupted paid call requires an explicit additional-charge retry; preserve old outputs, attempts and charges. Cancellation stops new work while preserving accepted provider work. Use the current image profiles for generative nodes, and the exact `google/gemini-2.5-flash` Gateway allowlist only for image descriptions, prompt enhancement and text utility nodes. Standard upscaling is local resampling; AI upscaling and expansion use model-specific settings and report actual returned dimensions.
- The pipeline worker is built from Git with `npm run build:pipeline-worker`, including the existing pinned CPU removal runtime. It uses PostgreSQL notifications and a bounded fallback check; the idle web app must not poll or perform detached paid work. The worker waits for the app's migration rather than migrating concurrently. Keep private S3/Gateway/database credentials server-side and out of native child processes. Pipeline local outputs and prepared references participate in daily processed-image retention. Archive downloads require fresh per-image permission/price checks, original bytes, backpressure, bounded count/bytes/concurrency and redacted errors.
- Post per-output charges and debit finite user credit atomically with generation/billing transitions. Use integer USD units at 12 decimal places, preserve sibling allocation totals, and never debit twice or revise a confirmed price. Default credit is unlimited; organization owners alone adjust their organization's user balances with an audit record. Unresolved costs remain outstanding rather than being assumed free. Finite accounts admit one unresolved batch and may overdraw on its final cost; block further batches at zero or negative credit.

## Authentication and request safety

- Never store configured usernames/passwords or other server credentials in client-readable cookies or browser storage.
- Authenticate through a server endpoint and issue a random opaque, expiring `HttpOnly`, `SameSite` session cookie backed by a hashed PostgreSQL session row. Use `Secure` in production/HTTPS, salted bounded scrypt password verification, and account-version revocation for password/role/enabled-state changes. The original configured login bootstraps the first organization owner once; it must never bypass an established account password.
- Scope every generation/history/log/detail/billing read and mutation to authenticated organization and user. Recheck image and mask access before paid work. Keep owner administration scoped to their organization and protect the last enabled owner. Browser mutations require exact same-origin validation.
- Bind private client cache keys and browser preferences to account identity. Discard asynchronous responses after an account epoch changes and clear other tabs through credential-free notifications without logging out their new session.
- Parse multipart uploads as bounded streams; enforce request, file-count, per-file, aggregate-byte, and concurrent-upload limits during consumption. Do not reintroduce whole-body multipart parsers for large image uploads.
- Keep all image reads, writes, listings, and serving confined to the configured S3 prefix. Validate canonical object-key segments, reject traversal/URLs/ambiguous encoding, paginate listings, and bound recursive deletions. Local import tools must resolve real paths and reject symlinks/junctions/reparse points.
- Determine trusted image MIME/extension from successfully decoded content, not caller filenames or magic prefixes alone. Reject corrupt, truncated, arbitrary ISO-BMFF/video, and unsupported image payloads before storage.
- Login and other credential-verification endpoints require bounded, process-wide attempt throttling in addition to timing-safe comparison.

## Database and migrations

- NEVER hand-edit generated files under `drizzle/` or `drizzle/meta/`.
- Change `server/db/schema.ts`, then generate with `npm run drizzle:generate -- --name=<name>` and review the generated SQL.
- Test migrations on a disposable/local database before applying them. Use `npm run drizzle:migrate`; do not use `drizzle:push` for schema changes in this project.
- Keep `drizzle-orm` and `drizzle-kit` pinned to the same tested v1 release, currently `1.0.0-rc.4`. PostgreSQL migration SQL and snapshots live together in timestamped folders under `drizzle/postgres/`; existing SQLite histories under `drizzle/` are retained as archives. Use `npm run drizzle:up` for a migration-format upgrade, review generated changes, and preserve existing SQL and migration timestamps. It is not a routine startup command. Never run migrations on each serverless cold start; apply them once through an explicit migration command.
- For a Drizzle upgrade, test fresh databases and existing v0 migration histories, including pending migrations, data preservation, repeated migration runs, and conditional generation updates. The v1 SQLite migrator upgrades its bookkeeping table when `npm run drizzle:migrate` runs.
- List/history endpoints must paginate in SQL and should not deserialize large per-generation metadata unless the caller requests details.

## Verification

- Add regression coverage for every model profile and settings discriminator, model switching, mask/source validation, timeouts, limiter overload/recovery, multi-output partial failures, pending-job recovery, auth sessions, upload limits, root confinement, and redacted errors. Account and sharing changes require cross-user/cross-organization privacy, revocation, role administration, private history, account switching, immutable replay sources, and bounded exact-key deletion coverage.
- Before handing off changes, run `npm test`, `npx nuxi typecheck`, `npm run build`, `npx drizzle-kit check`, and `git diff --check` when applicable.
- Do not make paid generation calls during routine tests.

## Production safety — non-negotiable

- NEVER deploy, redeploy, promote, restart, roll back, or otherwise mutate any production environment unless the user explicitly asks and confirms the exact action.
- NEVER use Railway CLI/API/MCP or another deployment tool to change production without that explicit confirmation. In particular, never run `railway up` against production or upload a local working tree directly to a production service.
- Production migrations, database writes, environment-variable changes, service configuration changes, and destructive production operations are forbidden by default.
- Production access is read-only: inspect status/logs/metrics only when requested.
